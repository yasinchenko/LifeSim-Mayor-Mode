Идеи для реализации:
1. Музыкальное сопровождение.
2. Отображение более наглядного потока государственных денег в симуляции. - Ок
3. Заставка игры.
4. Онбординг в виде анимации на странице меню.
5. Личный кабинет мэра: оффшор, покупки. Точки пополнения оффшора: карточки действий, баланс организаций в прямом подчинении: полиция, пожарные, коммунальные службы. Покупки: охрана (чем выше грейд, тем ниже вероятность убийства), вилла, дорогая машина, драгоценности, роскошь. - Ок
6. Вероятность убийства мэра. - Ок

План работ

1. Backend: модель личного кабинета - Ок

Добавить runtime-состояние mayorOffice.
Поля:
offshoreBalance;
corruption;
securityLevel;
luxuryLevel;
statusLevel;
riskLevel;
operations[].
Хранить в sim_config как JSON, по аналогии с district services/incidents/investments.

2. Backend: API - Ок

Добавить маршруты:
GET /mayor-office;
POST /mayor-office/skim-city-budget;
POST /mayor-office/skim-service-budget;
POST /mayor-office/provide-service;
POST /mayor-office/purchase.
Обновить OpenAPI и generated clients.

3. Backend: пополнение оффшора из бюджета города - Ок

3 уровня: 10%, 50%, 100% от допустимой суммы.
Важно: брать не весь бюджет, а только freeManagementBudget из прогноза казны, чтобы игрок не мог случайно мгновенно убить городскую систему.
Эффект:
governmentBudget -= amount;
offshoreBalance += amount;
corruption += scale;
репутация жителей/государства падает.

4. Backend: вывод из служб - Ок

MVP лучше трактовать как снижение эффективности службы, а не как отдельный бухгалтерский баланс службы.
Для района и службы применять временный/постоянный штраф:
меньше готовность службы;
выше шанс происшествий;
рост аварийности/падение безопасности.
Эффект:
offshore += amount;
corruption += scale;
ухудшение районной метрики по типу службы.

5. Backend: “оказать услугу” району - Ок

Сделать каталог сделок MVP:
деловой район: уплотнительная застройка;
рынок: серые разрешения;
кварталы: коммерческая застройка;
ратуша: административный подряд;
службы: скрытая оптимизация.
3 уровня: малый/средний/крупный.
Эффекты:
offshore +;
businessTrust +;
mayorReputationResidents -;
comfort/infrastructure/safety ухудшаются по типу сделки;
corruption +.

6. Backend: покупки - Ок

Каталог:
охрана: 5 000 / 20 000, повышает securityLevel;
вилла: +статус, +роскошь;
дорогая машина: +статус, +коррупционный раздражитель;
роскошь: +личное богатство/статус.
Все покупки списываются только из оффшора.
Роскошь при высокой бедности должна ухудшать жителей/государство.

7. Backend: риск мэра - Ок

Считать скрытый numeric risk из:
коррупции;
низкой репутации жителей;
активных протестов;
игнорированных/expired событий;
жёстких решений;
уровня охраны как понижающего множителя.
В API отдавать только статус:
low;
rising;
danger.
В MVP можно пока без убийства, только риск-статус и события-предупреждения.

8. Backend: альтернативная победа

В evaluateGoal() добавить условие:
если offshoreBalance >= 100000;
gameStatus === active;
мэр не смещён;
срок/цель достигнуты или достаточно дней прожито.
Лучше сделать это только для corruption_network, чтобы не ломать остальные сценарии.

9. Frontend: новая страница - Ок

Добавить /mayor-office.
В левый блок Состояние города добавить карточку Кабинет мэра.
На странице:
оффшор;
коррупция как статус, не сухая бухгалтерия;
риск мэру;
охрана;
блок Пополнить оффшор;
блок Оказать услугу;
блок Покупки;
история операций.

10. Frontend: тон и UX

Не делать это “магазином”.
Тексты должны звучать как политические решения:
Перенаправить резерв;
Закрыть вопрос со службой;
Согласовать интересы застройщика;
Усилить личный контур безопасности.
Показывать последствия до клика: оффшор +, репутация -, риск +.

11. Проверки

Typecheck/build.
Runtime-проверка API.
Проверка, что:
оффшор сохраняется;
новая партия сбрасывает кабинет;
старые сейвы не падают;
городская казна и прогноз казны обновляются после вывода денег;
районные метрики меняются после услуг.

Покупки охраны/роскоши.
Услуги района.
