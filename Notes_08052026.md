Пошаговый План

1. Зафиксировать MVP-границы
В MVP оставить только:

- 3 службы: коммунальная, полиция, пожарные;
- 3 происшествия: коммунальная авария, протест, пожар;
- найм сотрудников из безработных;
- реакция/игнорирование события;
- районное окно на карте.

2. Ввести модель районов
Создать постоянный список районов с id, названием и базовыми метриками:

безопасность;
комфорт;
аварийность;
доверие жителей;
доверие бизнеса;
бедность;
состояние инфраструктуры.
Важно: текущие районы из карты нужно превратить из визуальных карточек в данные симуляции.

3. Добавить состояние служб района
Для каждого района хранить:

количество коммунальщиков;
количество полицейских;
количество пожарных;
очередь найма;
сколько тиков осталось до выхода новых сотрудников;
расходы службы.

4. Добавить найм сотрудников
Логика:

источник кандидатов: безработные жители района;
если районная привязка жителей пока слабая, временно использовать существующий getResidentDistrict(agentId);
найм стоит бюджет;
сотрудник выходит через 3 тика;
зарплата фиксированная;
расход = зарплаты + 10% содержание.

5. Добавить районные события
Новая сущность districtIncident:

id;
districtId;
тип: fire, protest, utility_failure, staff_quit;
статус: active, resolved, ignored, expired;
дедлайн реакции;
сила события;
требуемая служба;
базовый штраф;
усиленный штраф при игнорировании.

6. Сделать генерацию событий
На тике или раз в игровой день рассчитывать вероятность:

плохая инфраструктура → больше аварий;
низкая безопасность → больше пожаров/беспорядков;
низкое доверие жителей → протесты;
нехватка сотрудников → выше шанс события;
хорошая служба района → ниже шанс события.

7. Добавить реакции игрока
Для активного события:

Отреагировать — требует нужную службу, снижает последствия;
Игнорировать или пропустить дедлайн — штраф x2 к репутации относительно обычных обращений;
если службы мало, реакция частичная.

8. Добавить инвестиции в район
MVP-инвестиции:

благоустройство;
безопасность;
инфраструктура;
бизнес-зона;
соцподдержка.
Каждая инвестиция должна иметь:

стоимость;
целевую метрику района;
побочные эффекты для репутации жителей/бизнеса/государства.

9. Обновить API
Добавить endpoints примерно такого состава:

GET /api/districts
GET /api/districts/:id
POST /api/districts/:id/hire
POST /api/districts/:id/invest
POST /api/district-incidents/:id/respond
POST /api/district-incidents/:id/ignore

10. Обновить карту
На карте района показывать:

индекс района;
количество активных происшествий;
цвет благополучия;
визуальный сигнал при активном событии.

11. Добавить окно района
По клику на район открывать панель:

метрики района;
службы и штат;
очередь найма;
активные события;
история событий;
инвестиции.

12. Связать с существующей экономикой
Механика должна влиять на:

бюджет города;
reputationResidents;
reputationBusiness;
reputationGovernment;
потребности жителей: physicalSafety, housingSafety, comfort, wellbeing;
бизнес-среду района.

13. Балансировка MVP
Начать с мягких значений:

0–2 события в день на весь город;
дедлайн реакции 1–2 дня;
штраф за игнорирование заметный, но не смертельный;
найм полезен, но не должен полностью отключать события.

14. Тестовый вертикальный срез
Сначала реализовать один район и один тип события:

коммунальная авария;
коммунальная служба;
найм;
реакция;
изменение комфорта/инфраструктуры.
После этого расширить на полицию, пожарных и остальные районы.


* Рекомендуемый порядок реализации

Районы как backend-сущность.
Службы района и найм.
Одно событие: коммунальная авария.
Реакция/игнорирование.
UI окна района.
Сигналы на карте.
Пожары и протесты.
Инвестиции.
Балансировка.

Главный риск: если сразу делать все службы, события и инвестиции, механика расползётся. Лучше идти через вертикальный срез “район → авария → служба → решение → последствия”.
